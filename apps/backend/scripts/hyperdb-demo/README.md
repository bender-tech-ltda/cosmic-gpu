# HyperDB awareness demo

A runnable, self-contained example that exercises [`hyperdb@6.x`](https://github.com/holepunchto/hyperdb) end-to-end. It is intentionally **not** wired into the backend runtime — the production state layer uses Hyperbee on Hypercore behind a `KvStore` interface (see [`apps/backend/src/state/`](../../src/state/)).

## Why this exists

The take-home brief explicitly names HyperDB:

> "the platform will use HyperDB as a distributed key-value store"

We evaluated `hyperdb@6.x` and chose **not** to use it as the production K/V backend. The full rationale lives in [`docs/architecture.md` §2.4 + §4](../../../../docs/architecture.md). This demo is the runnable evidence behind that decision: it proves we know HyperDB's actual API surface, and that the choice to use Hyperbee directly was deliberate, not avoidance.

## What it does

1. Opens a fresh Hypercore in a temp directory.
2. Wraps it in `HyperDB.bee(core, definition)` — the P2P-aware engine.
3. Inserts records into a `@cosmic/kv` collection and `flush()`-es them.
4. Reads one back via `db.get(...)`.
5. Streams a range scan via `db.find(...)` (the HyperDB equivalent of our `KvStore.list(prefix)`).
6. Deletes a record and re-reads to confirm.
7. Cleans up the temp directory.

## How to run

```bash
pnpm --filter @cosmic/backend demo:hyperdb
```

## File layout

```text
hyperdb-demo/
├── README.md            # this file
├── build-spec.cjs       # one-time codegen for the schema (CommonJS)
├── run.mjs              # the demo (ESM)
└── spec/                # generated; committed so the demo runs on a fresh checkout
    ├── hyperschema/     # output of Hyperschema.toDisk(...)
    │   ├── index.js     # CJS — the schema runtime
    │   └── schema.json  # the schema declaration
    └── hyperdb/         # output of HyperDB.toDisk(..., { esm: true })
        ├── index.js     # ESM — the runtime definition consumed by run.mjs
        ├── messages.js  # ESM — collection encoding helpers
        └── db.json      # the database declaration
```

## Re-generating the spec

If the schema needs to change (e.g. add a field to the `kv` collection), edit `build-spec.cjs` and re-run it:

```bash
node apps/backend/scripts/hyperdb-demo/build-spec.cjs
```

The generator overwrites `spec/`; commit the new output.

## What we learned

- HyperDB 6.x is a **schema-first document database**, not a generic K/V store. Every runtime call goes through a `definition` object that must be generated by the builder ahead of time.
- The runtime API is collection-scoped: `db.insert(collection, doc)`, `db.get(collection, queryObject)`, `db.find(collection, range)`. The `query` is not a string key — it is a partial record shape that HyperDB turns into a key via the collection's index.
- `db.flush()` is **mandatory** to persist a batch — none of `insert / delete / insertAll` write to the underlying Hyperbee on their own.
- The `bee` engine wraps a Hypercore directly, so it inherits Hypercore's append-only, signed-merkle-tree, P2P-replicable semantics. From a distributed-systems point of view this is the same substrate Hyperbee uses; the value HyperDB adds is the schema + indexing layer above it.

For our take-home — generic `key: string → JSON value` — the schema layer pays no dividend. We use Hyperbee directly. The `KvStore` interface keeps a future migration to a properly-typed HyperDB layout possible (e.g. one collection per resource: `apiKeys`, `workers`, `jobs`, `usage`) the moment we need typed queries.
